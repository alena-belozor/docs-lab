## 1. Что такое программная документация

### 1.1. Определение

**Программная документация** — это совокупность документов, описывающих программное средство: его назначение, устройство, порядок установки, использования и сопровождения. Документы могут быть бумажными, электронными, а также встроенными в сам продукт (например, справка в программе).

Важно различать два понятия:

- **Документ** — отдельный носитель информации (например, «Руководство пользователя»).
- **Документация** — весь комплект документов к программе.

### 1.2. Зачем нужна документация

Назову пять основных причин.

**Первая — передача знаний.** Знания о проекте не должны жить только в голове одного разработчика. В инженерной среде это называют «фактором автобуса» (bus factor): сколько человек должно «попасть под автобус», чтобы проект остановился. Если ответ «один», то проект находится в опасности. Документация увеличивает этот показатель.

**Вторая — ускорение вхождения новых людей в проект.** Хорошо написанное описание архитектуры и инструкция по развёртыванию окружения сокращают срок адаптации нового сотрудника с недель до дней.

**Третья — сопровождение.** По статистике, большая часть жизненного цикла программы приходится на этап сопровождения, а не разработки. Чтобы исправить ошибку через два года, нужно понимать, почему код написан именно так.

**Четвёртая — взаимодействие с заказчиком и пользователями.** Заказчик принимает продукт по документам: техническому заданию, руководству пользователя, акту. Пользователь без руководства может не узнать о половине возможностей программы.

**Пятая — юридическая и нормативная.** В ряде отраслей (медицина, авиация, государственные информационные системы) наличие документации — обязательное требование. Без неё продукт просто не будет принят или сертифицирован.

### 1.3. Документация и жизненный цикл ПО

**Жизненный цикл программного обеспечения** — это период от появления идеи до вывода программы из эксплуатации. Он включает этапы: анализ требований, проектирование, реализацию, тестирование, внедрение, сопровождение.

На каждом этапе создаются свои документы:

| Этап | Типичные документы |
|---|---|
| Анализ требований | Техническое задание, спецификация требований |
| Проектирование | Описание архитектуры, схемы базы данных, диаграммы UML |
| Реализация | Комментарии в коде, описание API |
| Тестирование | План тестирования, тест-кейсы, отчёт о тестировании |
| Внедрение | Руководство по установке, руководство администратора |
| Сопровождение | Руководство пользователя, журнал изменений, база known issues |

Таким образом, документирование — это не отдельный этап «в конце», а непрерывный процесс, идущий параллельно с разработкой.

## 2. Виды документации

Документацию принято делить по аудитории: для кого она написана. Это самый практичный способ классификации.

### 2.1. Документация для пользователей

Её читают люди, которые используют программу, но не обязаны знать, как она устроена.

- **Руководство пользователя** — пошаговое описание работы с программой. Пример: «Как оформить заказ в интернет-магазине».
- **Справочная система** (help) — встроенная справка, часто с поиском.
- **FAQ** (Frequently Asked Questions) — список часто задаваемых вопросов с ответами.
- **Обучающие материалы** — видеоуроки, интерактивные туториалы (tutorial — обучающее руководство, ведущее пользователя шаг за шагом).
- **Примечания к выпуску** (release notes) — что нового в версии.

Главное требование: простой язык, минимум терминов, много иллюстраций и примеров.

### 2.2. Документация для администраторов

Её читают специалисты, которые устанавливают и поддерживают программу на серверах.

- **Руководство по установке и настройке.**
- **Руководство администратора.**
- **Описание параметров конфигурации.**
- **Инструкции по резервному копированию и восстановлению.**
- **Описание мониторинга и действий при сбоях** (runbook — «книга действий» на случай инцидентов).

### 2.3. Документация для разработчиков

Самый обширный раздел. Её читают те, кто пишет и меняет код.

- **Описание архитектуры** — из каких компонентов состоит система и как они взаимодействуют.
- **Описание структуры базы данных** (ER-диаграммы).
- **Документация по API** — описание того, какие функции и методы программа предоставляет другим программам.
- **Комментарии и docstring в коде.**
- **Руководство для контрибьюторов** (CONTRIBUTING.md) — как предложить изменения в проекте, как оформлять код и коммиты.
- **Журнал архитектурных решений** (ADR — Architecture Decision Records): короткие записи вида «мы выбрали PostgreSQL, потому что… рассматривали MongoDB, но отказались, потому что…».

### 2.4. Проектная и управленческая документация

- Техническое задание.
- План проекта, график работ.
- Отчёты о ходе работ.
- Протоколы встреч.

### 2.5. Документация по тестированию

- **План тестирования** — что, как и когда тестируем.
- **Тест-кейс** — описание одного проверочного сценария: исходные данные, шаги, ожидаемый результат.
- **Отчёт о дефектах** (bug report).

Пример тест-кейса:

| Поле | Значение |
|---|---|
| Название | Вход с неверным паролем |
| Шаги | 1. Открыть страницу входа. 2. Ввести корректный логин и неверный пароль. 3. Нажать «Войти». |
| Ожидаемый результат | Сообщение «Неверный логин или пароль», вход не выполнен |

## 3. Стандарты документирования

### 3.1. Зачем нужны стандарты

**Стандарт** — это документ, устанавливающий единые правила, требования и характеристики. Для документации стандарты определяют: какие документы должны быть, какие разделы в них входят, как их оформлять.

Преимущества стандартизации: единообразие, предсказуемость (читатель знает, где искать нужную информацию), упрощение приёмки.

### 3.2. ЕСПД — ГОСТ 19

**ЕСПД** — Единая система программной документации. Это комплекс российских (ранее советских) стандартов серии ГОСТ 19. Наиболее известные из них:

- **ГОСТ 19.101** — виды программных документов.
- **ГОСТ 19.102** — стадии разработки.
- **ГОСТ 19.201** — Техническое задание. Требования к содержанию и оформлению.
- **ГОСТ 19.301** — Программа и методика испытаний.
- **ГОСТ 19.401** — Текст программы.
- **ГОСТ 19.402** — Описание программы.
- **ГОСТ 19.502** — Описание применения.
- **ГОСТ 19.503** — Руководство системного программиста.
- **ГОСТ 19.504** — Руководство программиста.
- **ГОСТ 19.505** — Руководство оператора.

Например, по ГОСТ 19.201 техническое задание содержит разделы: введение, основания для разработки, назначение разработки, требования к программе или программному изделию, требования к программной документации, технико-экономические показатели, стадии и этапы разработки, порядок контроля и приёмки.

Часто на практике, например при сдаче работ государственному заказчику, требуется именно оформление по ЕСПД.

### 3.3. ГОСТ 34 — автоматизированные системы

Для **автоматизированных систем** (АС) действует серия ГОСТ 34. Главный документ — ГОСТ 34.602, он определяет содержание технического задания на создание АС. Разница с ГОСТ 19 в том, что ГОСТ 34 описывает систему целиком (программы, оборудование, персонал), а ГОСТ 19 — именно программное средство.

### 3.4. ГОСТ Р ИСО/МЭК 12207 и 15289

**ГОСТ Р ИСО/МЭК 12207** — российский аналог международного стандарта ISO/IEC 12207 «Процессы жизненного цикла программных средств». Он описывает процессы, в том числе процесс документирования.

**ISO/IEC/IEEE 15289** — международный стандарт, определяющий, какая информация должна быть в документах жизненного цикла.

### 3.5. Современная практика

В коммерческой разработке (особенно в IT-компаниях, работающих по гибким методологиям) жёсткие ГОСТ применяют реже. Здесь действует принцип, закреплённый в Agile Manifesto: «работающее программное обеспечение важнее исчерпывающей документации». Но важно понимать: **это не означает «документация не нужна»**. Это означает «не нужно писать документы ради документов». Пишут то, что реально нужно людям.

## 4. Документация в исходном коде

### 4.1. Комментарии

**Комментарий** — это текст в исходном коде, который игнорируется компилятором или интерпретатором и предназначен для человека.

Золотое правило: **хороший комментарий объясняет «почему», а не «что»**. Что делает код, видно из самого кода. А вот почему он написан именно так — не видно.

Плохой комментарий:

```python
# Увеличиваем i на 1
i = i + 1
```

Он дублирует очевидное.

Хороший комментарий:

```python
# API банка возвращает суммы в копейках, переводим в рубли
amount = response["amount"] / 100
```

Здесь комментарий сообщает то, что из кода не вытекает: особенность внешней системы.

Виды комментариев:

- **Однострочные** (`# ...` в Python, `// ...` в C++ и Java).
- **Многострочные** (`/* ... */` в C-подобных языках).
- **Служебные пометки:** `TODO` (нужно сделать), `FIXME` (нужно исправить), `HACK` (временное решение). Они помогают не забыть о долге, но не должны копиться годами.

### 4.2. Самодокументируемый код

**Самодокументируемый код** — код, который понятен без комментариев благодаря хорошим именам и структуре.

Сравните:

```python
def f(a, b):
    return a * b * 0.2
```

и

```python
def calculate_vat(price, quantity):
    VAT_RATE = 0.2
    return price * quantity * VAT_RATE
```

Во втором случае комментарии не нужны: по именам всё понятно. Принцип: сначала пытаемся сделать код понятным, и только потом добавляем комментарии для того, что выразить кодом нельзя.

### 4.3. Docstring

**Docstring** (строка документации) — это специальный строковый литерал, который размещается в начале модуля, класса или функции и описывает их назначение. В Python docstring доступен во время выполнения через `help()` и атрибут `__doc__`, и именно из него генераторы документации строят справку.

Пример (формат Google style):

```python
def divide(a, b):
    """Делит одно число на другое.

    Args:
        a (float): Делимое.
        b (float): Делитель, не должен быть равен нулю.

    Returns:
        float: Результат деления a на b.

    Raises:
        ZeroDivisionError: Если b равно нулю.

    Example:
        >>> divide(10, 4)
        2.5
    """
    return a / b
```

Структура хорошего docstring: краткое описание в одной строке, подробности, параметры, возвращаемое значение, исключения, пример использования.

Основные стили оформления docstring в Python: Google style, NumPy style, reStructuredText (стиль Sphinx). Важно выбрать один стиль на весь проект.

### 4.4. Аннотации типов

**Аннотации типов** (type hints) — это явное указание типов параметров и возвращаемых значений. Они тоже являются формой документации:

```python
def divide(a: float, b: float) -> float:
    return a / b
```

Читателю сразу ясно, что функция принимает и что возвращает. Кроме того, инструменты (например, mypy) могут проверять соответствие типов автоматически.

## 5. Генераторы документации

### 5.1. Идея

Писать справочную документацию по API вручную долго и ненадёжно: код меняется, а текст устаревает. Поэтому придумали **генераторы документации** — программы, которые читают исходный код вместе с комментариями и docstring и автоматически создают из них готовые страницы (HTML, PDF).

Принцип: **единый источник истины**. Описание лежит рядом с кодом, меняется вместе с ним, а итоговый документ собирается автоматически.

### 5.2. Популярные инструменты

| Инструмент | Языки | Формат комментариев |
|---|---|---|
| **Sphinx** | Python | reStructuredText, docstring |
| **MkDocs** | любые (пишутся .md-файлы) | Markdown |
| **Doxygen** | C, C++, Java, Python и др. | специальные теги `@param`, `@return` |
| **Javadoc** | Java | теги `@param`, `@return`, `@throws` |
| **JSDoc** | JavaScript | теги `@param`, `@returns` |
| **Rustdoc** | Rust | Markdown в комментариях `///` |
| **Godoc** | Go | обычные комментарии перед объявлением |

### 5.3. Пример: Javadoc

```java
/**
 * Вычисляет площадь прямоугольника.
 *
 * @param width  ширина, должна быть положительной
 * @param height высота, должна быть положительной
 * @return площадь прямоугольника
 * @throws IllegalArgumentException если width или height не положительны
 */
public double area(double width, double height) {
    if (width <= 0 || height <= 0) {
        throw new IllegalArgumentException("Размеры должны быть положительными");
    }
    return width * height;
}
```

После запуска команды `javadoc` получим набор HTML-страниц с описанием класса, методов, параметров. Именно так выглядит официальная документация стандартной библиотеки Java.

### 5.4. Пример: Sphinx

Базовый порядок работы со Sphinx:

1. Установить: `pip install sphinx`.
2. Создать каркас документации: `sphinx-quickstart`.
3. Подключить расширение `sphinx.ext.autodoc`, которое умеет брать docstring из кода.
4. В файле `.rst` указать, какой модуль документировать:

```rst
.. automodule:: mymodule
   :members:
```

5. Собрать: `make html`.

На выходе — готовый сайт документации. Именно на Sphinx построена документация самого Python и множества библиотек.

### 5.5. Doxygen

Doxygen позволяет, помимо текста, строить диаграммы классов и графы вызовов функций (при наличии Graphviz). Это удобно для больших проектов на C++, где нужно «увидеть» структуру.

## 6. Markdown и README

### 6.1. Markdown

**Markdown** — лёгкий язык разметки, в котором форматирование задаётся простыми символами. Например:

```markdown
# Заголовок первого уровня
## Заголовок второго уровня

Обычный текст, **жирный**, *курсив*.

- пункт списка
- ещё пункт

[Ссылка](https://example.com)
```

Его главные плюсы:

- Читается как обычный текст даже без обработки.
- Файлы небольшие и текстовые, поэтому **отлично работают с Git** (видно, что именно изменилось в каждой строке).
- Поддерживается GitHub, GitLab и большинством платформ.

### 6.2. README

**README** — это файл в корне репозитория, который читают первым. По сути это «лицо» проекта. Хороший README отвечает на вопросы:

1. Что это за проект и зачем он нужен?
2. Как его установить?
3. Как запустить и быстро попробовать?
4. Как им пользоваться (примеры)?
5. Как внести вклад?
6. Под какой лицензией он распространяется?

Пример минимального README:

```markdown
# TaskTracker

Консольная программа для учёта задач.

## Установка
    pip install tasktracker

## Быстрый старт
    tasktracker add "Подготовить доклад"
    tasktracker list

## Лицензия
MIT
```

Рекомендация: если по README новый человек не смог запустить проект за 10 минут, README нужно доработать.

### 6.3. Другие файлы в репозитории

- **CHANGELOG.md** — журнал изменений по версиям. Принято вести по формату Keep a Changelog.
- **CONTRIBUTING.md** — правила участия.
- **LICENSE** — лицензия.
- **CODE_OF_CONDUCT.md** — правила поведения в сообществе.

## 7. Docs as Code: документация как код

> Далее докладчик: Круглова Злата

### 7.1. Идея подхода

**Docs as Code** («документация как код») — подход, при котором с документацией работают теми же инструментами и по тем же правилам, что и с исходным кодом:

- документы хранятся в **системе контроля версий** (Git);
- пишутся в текстовых форматах (Markdown, reStructuredText, AsciiDoc);
- изменения проходят **ревью** через pull request;
- сборка и публикация автоматизированы через **CI/CD**.

### 7.2. Связь с Git

Раз уж наша лабораторная посвящена Git, остановимся на связи подробнее.

Git даёт документации:

1. **История изменений.** Можно увидеть, кто, когда и зачем изменил любой абзац (`git log`, `git blame`).
2. **Ветвление.** Новую главу руководства можно писать в отдельной ветке и не мешать остальным, а потом слить в основную (`git merge`).
3. **Совместная работа.** Несколько человек редактируют разные части документации, а возникающие конфликты решаются так же, как конфликты в коде.
4. **Ревью.** Через pull request коллега проверяет текст до того, как он попадёт в основную ветку.
5. **Привязка к версиям.** Документацию версии 2.0 можно получить, переключившись на соответствующий тег.

Типичный порядок работы над документацией:

```
git checkout -b docs/install-guide     # создаём ветку
# пишем текст
git add docs/install.md
git commit -m "добавлено руководство по установке"
git push origin docs/install-guide
# создаём pull request, коллега проверяет, затем слияние в main
```

### 7.3. Связь с CI/CD

**CI/CD** (Continuous Integration / Continuous Delivery — непрерывная интеграция и доставка) — практика автоматической сборки, проверки и публикации продукта при каждом изменении.

Для документации CI/CD делает следующее:

- при каждом изменении в основной ветке автоматически собирает сайт документации;
- проверяет корректность ссылок и орфографию;
- публикует результат, например на GitHub Pages.

Таким образом, документация всегда соответствует текущему состоянию кода, а вручную ничего публиковать не нужно.

Упрощённый пример конфигурации GitHub Actions:

```yaml
name: Docs
on:
  push:
    branches: [main]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pip install mkdocs
      - run: mkdocs gh-deploy --force
```

Что здесь происходит: при каждом push в ветку main запускается задача, она скачивает репозиторий, ставит MkDocs и публикует собранный сайт.

### 7.4. Плюсы подхода

- Документация не отрывается от кода.
- Разработчики охотнее её обновляют, потому что работают в привычной среде.
- Качество растёт за счёт ревью.
- Всё прозрачно и воспроизводимо.

## 8. Документирование API

### 8.1. Что такое API

**API** (Application Programming Interface — программный интерфейс приложения) — набор правил, по которым одна программа может обращаться к другой. Например, мобильное приложение погоды обращается к API сервера погоды, чтобы получить прогноз.

Документация API — это руководство для программистов, которые будут этот интерфейс использовать. Если API плохо описан, им не будут пользоваться, как бы хорошо он ни был реализован.

### 8.2. Что должно быть в описании

Для каждой операции (метода) указывают:

- адрес (URL) и HTTP-метод (GET, POST, PUT, DELETE);
- параметры запроса: название, тип, обязательность;
- пример запроса;
- формат ответа и пример;
- коды ошибок и их смысл;
- требования к аутентификации.

Пример описания:

```
GET /api/users/{id}

Возвращает информацию о пользователе.

Параметры:
  id (integer, обязательный) — идентификатор пользователя.

Ответ 200:
  {"id": 5, "name": "Анна", "email": "anna@example.com"}

Ответ 404:
  {"error": "Пользователь не найден"}
```

### 8.3. OpenAPI и Swagger

**OpenAPI** — открытая спецификация для описания REST API в машиночитаемом формате (YAML или JSON). **Swagger** — набор инструментов вокруг этой спецификации, в частности Swagger UI, который по описанию строит интерактивную страницу: на ней можно прямо в браузере отправить тестовый запрос.

Фрагмент спецификации:

```yaml
openapi: 3.0.0
info:
  title: Users API
  version: 1.0.0
paths:
  /users/{id}:
    get:
      summary: Получить пользователя
      parameters:
        - name: id
          in: path
          required: true
          schema:
            type: integer
      responses:
        '200':
          description: Успешно
        '404':
          description: Пользователь не найден
```

Преимущества: по такому файлу автоматически создаются документация, клиентские библиотеки, заготовки серверного кода и тесты. Многие фреймворки (FastAPI, Spring) умеют генерировать спецификацию прямо из кода.

## 9. Качество документации

### 9.1. Требования к хорошей документации

- **Актуальность.** Устаревшая документация хуже, чем её отсутствие, потому что вводит в заблуждение.
- **Полнота.** Описаны все важные сценарии.
- **Точность.** Примеры работают.
- **Ясность.** Простой язык, короткие предложения, термины объяснены.
- **Структурированность.** Оглавление, заголовки, навигация, поиск.
- **Ориентация на аудиторию.** Текст для администратора и текст для пользователя пишутся по-разному.

### 9.2. Типичные ошибки

1. **Документацию пишут в самом конце**, в спешке, когда уже ничего не помнят.
2. **Документация устаревает**, потому что её никто не обновляет вместе с кодом.
3. **Слишком много текста** — никто не читает, всё важное тонет.
4. **Нет примеров** — читатель не понимает, как применить описанное.
5. **Комментарии, дублирующие код.**
6. **Нет ответственного.** Если за документацию отвечают «все», то не отвечает никто.
7. **Документация хранится отдельно от кода** (в чужих файлах, на личных дисках) и теряется.
8. **Используются неопределённые термины и аббревиатуры** без расшифровки.

### 9.3. Как поддерживать актуальность

- Включить обновление документации в **Definition of Done** (критерии готовности задачи): задача считается выполненной, только если изменена и документация.
- Проверять документацию на ревью вместе с кодом.
- Использовать генерацию из кода.
- Автоматически проверять ссылки и примеры.
- Назначить ответственных.

## 10. Практический пример

Рассмотрим небольшой учебный проект: программа «Калькулятор» на Python. Покажем, как для неё выглядит минимальный, но полноценный комплект документации.

### 10.1. Структура репозитория

```
calculator/
├── README.md
├── CHANGELOG.md
├── LICENSE
├── calculator.py
├── tests/
│   └── test_calculator.py
└── docs/
    ├── user-guide.md
    └── architecture.md
```

### 10.2. Код с docstring

```python
"""Модуль calculator: простые арифметические операции."""


def add(a: float, b: float) -> float:
    """Возвращает сумму двух чисел."""
    return a + b


def divide(a: float, b: float) -> float:
    """Делит a на b.

    Raises:
        ZeroDivisionError: если b равно нулю.
    """
    if b == 0:
        raise ZeroDivisionError("Деление на ноль")
    return a / b
```

### 10.3. README.md

```markdown
# Calculator

Учебная библиотека простых арифметических операций.

## Установка
    git clone https://github.com/user/calculator.git

## Использование
    from calculator import add, divide
    print(add(2, 3))      # 5
    print(divide(10, 4))  # 2.5

## Тесты
    python -m unittest discover tests
```

### 10.4. CHANGELOG.md

```markdown
# Журнал изменений

## [1.1.0] — 2026-11-10
### Добавлено
- Функция divide с проверкой деления на ноль.

## [1.0.0] — 2026-11-01
### Добавлено
- Функция add.
```

### 10.5. Руководство пользователя (фрагмент)

> **Как вычислить сумму.** Подключите модуль командой `from calculator import add`. Вызовите функцию, передав два числа: `add(2, 3)`. Результат — число 5.
>
> **Что делать при ошибке «Деление на ноль».** Эта ошибка возникает, если вторым аргументом функции `divide` передан ноль. Проверьте введённые данные.

### 10.6. Что показывает пример

- Назначение и быстрый старт видны из README.
- Подробности каждой функции — в docstring, из которых можно собрать справку.
- История изменений — в CHANGELOG.
- Всё это лежит в Git и меняется вместе с кодом.

## 11. Тенденции

Коротко о том, что меняется сегодня:

- **Интерактивность:** документация, в которой примеры кода можно запускать прямо на странице.
- **Автоматизация:** генерация из кода и из схем API.
- **Поиск и ИИ-помощники,** которые отвечают на вопросы по документации. Но они не заменяют хорошо написанные первоисточники, а опираются на них: если исходный текст плох, плохим будет и ответ.
- **Документация как продукт:** над ней работают технические писатели (technical writers) — отдельная профессия.

## Заключение

Подведём итоги.

1. Документация — неотъемлемая часть программного продукта, а не «довесок».
2. Виды документации определяются аудиторией: пользователи, администраторы, разработчики, менеджеры, тестировщики.
3. Существуют стандарты (ЕСПД, ГОСТ 34, ISO/IEC 12207), но в современной практике главное — полезность документа для читателя.
4. Первый уровень документации — сам код: понятные имена, комментарии, объясняющие «почему», docstring и аннотации типов.
5. Генераторы документации (Sphinx, Doxygen, Javadoc) превращают описание в коде в готовые справочники.
6. README, CHANGELOG и другие файлы в репозитории — минимальный обязательный набор.
7. Подход Docs as Code объединяет документацию с Git и CI/CD: версионирование, ревью, автоматическая сборка.
8. Основные враги документации — устаревание и отсутствие ответственного.

И главная мысль: **документацию пишут не для галочки, а для людей — в том числе для себя самого через полгода.**

Спасибо за внимание! Готов ответить на вопросы.
