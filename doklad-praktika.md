## 7. Docs as Code: документация как код

### 7.1. Идея подхода

**Docs as Code** («документация как код») — подход, при котором с документацией работают теми же инструментами и по тем же правилам, что и с исходным кодом:

- документы хранятся в **системе контроля версий** (Git);
- пишутся в текстовых форматах (Markdown, reStructuredText, AsciiDoc);
- изменения проходят **ревью** через pull request;
- сборка и публикация автоматизированы через **CI/CD**.

### 7.2. Связь с Git

Раз уж наша лабораторная посвящена Git, остановимся на связи подробнее.

Git даёт документации:

1. **История изменений.** Можно увидеть, кто, когда и зачем изменил любой абзац (`git log`, `git blame`).
2. **Ветвление.** Новую главу руководства можно писать в отдельной ветке и не мешать остальным, а потом слить в основную (`git merge`).
3. **Совместная работа.** Несколько человек редактируют разные части документации, а возникающие конфликты решаются так же, как конфликты в коде.
4. **Ревью.** Через pull request коллега проверяет текст до того, как он попадёт в основную ветку.
5. **Привязка к версиям.** Документацию версии 2.0 можно получить, переключившись на соответствующий тег.

Типичный порядок работы над документацией:

```
git checkout -b docs/install-guide     # создаём ветку
# пишем текст
git add docs/install.md
git commit -m "добавлено руководство по установке"
git push origin docs/install-guide
# создаём pull request, коллега проверяет, затем слияние в main
```

### 7.3. Связь с CI/CD

**CI/CD** (Continuous Integration / Continuous Delivery — непрерывная интеграция и доставка) — практика автоматической сборки, проверки и публикации продукта при каждом изменении.

Для документации CI/CD делает следующее:

- при каждом изменении в основной ветке автоматически собирает сайт документации;
- проверяет корректность ссылок и орфографию;
- публикует результат, например на GitHub Pages.

Таким образом, документация всегда соответствует текущему состоянию кода, а вручную ничего публиковать не нужно.

Упрощённый пример конфигурации GitHub Actions:

```yaml
name: Docs
on:
  push:
    branches: [main]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pip install mkdocs
      - run: mkdocs gh-deploy --force
```

Что здесь происходит: при каждом push в ветку main запускается задача, она скачивает репозиторий, ставит MkDocs и публикует собранный сайт.

### 7.4. Плюсы подхода

- Документация не отрывается от кода.
- Разработчики охотнее её обновляют, потому что работают в привычной среде.
- Качество растёт за счёт ревью.
- Всё прозрачно и воспроизводимо.

## 8. Документирование API

### 8.1. Что такое API

**API** (Application Programming Interface — программный интерфейс приложения) — набор правил, по которым одна программа может обращаться к другой. Например, мобильное приложение погоды обращается к API сервера погоды, чтобы получить прогноз.

Документация API — это руководство для программистов, которые будут этот интерфейс использовать. Если API плохо описан, им не будут пользоваться, как бы хорошо он ни был реализован.

### 8.2. Что должно быть в описании

Для каждой операции (метода) указывают:

- адрес (URL) и HTTP-метод (GET, POST, PUT, DELETE);
- параметры запроса: название, тип, обязательность;
- пример запроса;
- формат ответа и пример;
- коды ошибок и их смысл;
- требования к аутентификации.

Пример описания:

```
GET /api/users/{id}

Возвращает информацию о пользователе.

Параметры:
  id (integer, обязательный) — идентификатор пользователя.

Ответ 200:
  {"id": 5, "name": "Анна", "email": "anna@example.com"}

Ответ 404:
  {"error": "Пользователь не найден"}
```

### 8.3. OpenAPI и Swagger

**OpenAPI** — открытая спецификация для описания REST API в машиночитаемом формате (YAML или JSON). **Swagger** — набор инструментов вокруг этой спецификации, в частности Swagger UI, который по описанию строит интерактивную страницу: на ней можно прямо в браузере отправить тестовый запрос.

Фрагмент спецификации:

```yaml
openapi: 3.0.0
info:
  title: Users API
  version: 1.0.0
paths:
  /users/{id}:
    get:
      summary: Получить пользователя
      parameters:
        - name: id
          in: path
          required: true
          schema:
            type: integer
      responses:
        '200':
          description: Успешно
        '404':
          description: Пользователь не найден
```

Преимущества: по такому файлу автоматически создаются документация, клиентские библиотеки, заготовки серверного кода и тесты. Многие фреймворки (FastAPI, Spring) умеют генерировать спецификацию прямо из кода.

## 9. Качество документации

### 9.1. Требования к хорошей документации

- **Актуальность.** Устаревшая документация хуже, чем её отсутствие, потому что вводит в заблуждение.
- **Полнота.** Описаны все важные сценарии.
- **Точность.** Примеры работают.
- **Ясность.** Простой язык, короткие предложения, термины объяснены.
- **Структурированность.** Оглавление, заголовки, навигация, поиск.
- **Ориентация на аудиторию.** Текст для администратора и текст для пользователя пишутся по-разному.

### 9.2. Типичные ошибки

1. **Документацию пишут в самом конце**, в спешке, когда уже ничего не помнят.
2. **Документация устаревает**, потому что её никто не обновляет вместе с кодом.
3. **Слишком много текста** — никто не читает, всё важное тонет.
4. **Нет примеров** — читатель не понимает, как применить описанное.
5. **Комментарии, дублирующие код.**
6. **Нет ответственного.** Если за документацию отвечают «все», то не отвечает никто.
7. **Документация хранится отдельно от кода** (в чужих файлах, на личных дисках) и теряется.
8. **Используются неопределённые термины и аббревиатуры** без расшифровки.

### 9.3. Как поддерживать актуальность

- Включить обновление документации в **Definition of Done** (критерии готовности задачи): задача считается выполненной, только если изменена и документация.
- Проверять документацию на ревью вместе с кодом.
- Использовать генерацию из кода.
- Автоматически проверять ссылки и примеры.
- Назначить ответственных.

## 10. Практический пример

Рассмотрим небольшой учебный проект: программа «Калькулятор» на Python. Покажем, как для неё выглядит минимальный, но полноценный комплект документации.

### 10.1. Структура репозитория

```
calculator/
├── README.md
├── CHANGELOG.md
├── LICENSE
├── calculator.py
├── tests/
│   └── test_calculator.py
└── docs/
    ├── user-guide.md
    └── architecture.md
```

### 10.2. Код с docstring

```python
"""Модуль calculator: простые арифметические операции."""


def add(a: float, b: float) -> float:
    """Возвращает сумму двух чисел."""
    return a + b


def divide(a: float, b: float) -> float:
    """Делит a на b.

    Raises:
        ZeroDivisionError: если b равно нулю.
    """
    if b == 0:
        raise ZeroDivisionError("Деление на ноль")
    return a / b
```

### 10.3. README.md

```markdown
# Calculator

Учебная библиотека простых арифметических операций.

## Установка
    git clone https://github.com/user/calculator.git

## Использование
    from calculator import add, divide
    print(add(2, 3))      # 5
    print(divide(10, 4))  # 2.5

## Тесты
    python -m unittest discover tests
```

### 10.4. CHANGELOG.md

```markdown
# Журнал изменений

## [1.1.0] — 2026-11-10
### Добавлено
- Функция divide с проверкой деления на ноль.

## [1.0.0] — 2026-11-01
### Добавлено
- Функция add.
```

### 10.5. Руководство пользователя (фрагмент)

> **Как вычислить сумму.** Подключите модуль командой `from calculator import add`. Вызовите функцию, передав два числа: `add(2, 3)`. Результат — число 5.
>
> **Что делать при ошибке «Деление на ноль».** Эта ошибка возникает, если вторым аргументом функции `divide` передан ноль. Проверьте введённые данные.

### 10.6. Что показывает пример

- Назначение и быстрый старт видны из README.
- Подробности каждой функции — в docstring, из которых можно собрать справку.
- История изменений — в CHANGELOG.
- Всё это лежит в Git и меняется вместе с кодом.

## 11. Тенденции

Коротко о том, что меняется сегодня:

- **Интерактивность:** документация, в которой примеры кода можно запускать прямо на странице.
- **Автоматизация:** генерация из кода и из схем API.
- **Поиск и ИИ-помощники,** которые отвечают на вопросы по документации. Но они не заменяют хорошо написанные первоисточники, а опираются на них: если исходный текст плох, плохим будет и ответ.
- **Документация как продукт:** над ней работают технические писатели (technical writers) — отдельная профессия.

## Заключение

Подведём итоги.

1. Документация — неотъемлемая часть программного продукта, а не «довесок».
2. Виды документации определяются аудиторией: пользователи, администраторы, разработчики, менеджеры, тестировщики.
3. Существуют стандарты (ЕСПД, ГОСТ 34, ISO/IEC 12207), но в современной практике главное — полезность документа для читателя.
4. Первый уровень документации — сам код: понятные имена, комментарии, объясняющие «почему», docstring и аннотации типов.
5. Генераторы документации (Sphinx, Doxygen, Javadoc) превращают описание в коде в готовые справочники.
6. README, CHANGELOG и другие файлы в репозитории — минимальный обязательный набор.
7. Подход Docs as Code объединяет документацию с Git и CI/CD: версионирование, ревью, автоматическая сборка.
8. Основные враги документации — устаревание и отсутствие ответственного.

И главная мысль: **документацию пишут не для галочки, а для людей — в том числе для себя самого через полгода.**
